**What works:**
- Full Docker stack runs and all three containers are healthy
- API health check: `GET /api/v1/health` → `{"status":"healthy"}`
- Auth (OIDC, off unless configured): production values (Logto app `finance-sentry`, authority `https://lifekit-vps.tail1cb676.ts.net:3001/oidc`, public base `https://lifekit-vps.tail1cb676.ts.net:4200`, redirect `/api/v1/auth/oidc/signin`) live in `docker/.env.sops`; `Auth:Oidc:{Authority,ClientId,ClientSecret,PublicBaseUrl,RequireHttpsMetadata}` (env `AUTH_OIDC_*`, secret via `docker/.env.sops`) registers an `AddOpenIdConnect("lifekit")` scheme (code + PKCE, confidential, `openid email profile`) on Identity's external cookie. `GET /api/v1/auth/oidc/start[?returnUrl=]` challenges; the provider returns to `/api/v1/auth/oidc/signin`, then `GET /auth/oidc/callback` requires `email_verified`, runs `ExternalLoginCommand("lifekit", sub, …)` (invite required, lockout honoured, relink by verified email), sets the usual refresh/access cookies and redirects to the SPA (failures to `/login?error=<code>`, with `ACCOUNT_UNAVAILABLE` for locked/revoked). `PublicBaseUrl` is explicit because the nginx proxy hides the public host. `BackchannelAuthority` (prod default `http://logto:3001/oidc`, over the external `identity-oidc` network that `deploy.sh` creates idempotently) re-bases only the API's own discovery/JWKS/token/userinfo calls (`OidcAuthorityRewriteHandler`); the validated issuer and the browser redirect keep the public `Authority`. A plain-HTTP back channel forces `RequireHttpsMetadata` off (the provider advertises its JWKS/endpoints on the host it was asked on); otherwise the configured value (default true) applies. `GET /auth/methods` tells the SPA which of OIDC/password/Google to offer; with OIDC on the login page shows one "Sign in" button and invite-accept becomes "You're invited". Password and Google-direct stay governed by their flags. In production the Google-direct button is off by default (`Auth__GoogleDirect__Enabled` ← `AUTH_GOOGLE_DIRECT_ENABLED`, default `false` in `docker-compose.prod.yml`); set `AUTH_GOOGLE_DIRECT_ENABLED=true` and redeploy to turn it back on. Dev/test and the appsettings default keep it on.
- Auth: invite-only. Login and Google sign-in work for existing accounts only; there is no self sign-up (`auth/register` is gone). People (`/settings/people`, `users.manage`; REST `GET /api/v1/people`, `POST /people/invites`, `POST /people/{userId}/revoke`): an invite creates a Member account with no password (`UserManager.CreateAsync`) and returns a one-time link built from `GeneratePasswordResetTokenAsync` (lifespan `AuthModule.InviteLifespan`, 7 days; there is no mailer, the owner sends it); `POST /auth/invite/accept` (anonymous) sets the password with `ResetPasswordAsync` and signs the person in. Password login on a locked-out account (Identity lockout after repeated failures) is 429 `ACCOUNT_LOCKED` with a `Retry-After` header and a message giving the remaining minutes, shown on the login form; a revoked person (indefinite lockout) and unknown email vs wrong password keep the generic 401 `INVALID_CREDENTIALS`. Google sign-in verifies the credential, then hands off to the provider-agnostic `ExternalLoginCommand` (`provider`, `subject`, `email`, `emailVerified`), which matches an existing account by provider-verified email and links it through `AspNetUserLogins` (an unknown or unverified email is 403 `ACCOUNT_NOT_INVITED`); a further external provider reuses that handler. `Auth:PasswordLogin:Enabled` and `Auth:GoogleDirect:Enabled` (`AuthSignInOptions`, both default on) switch password login and direct Google sign-in off; a disabled method is 403 `SIGN_IN_METHOD_DISABLED` (registry text "This sign-in method is not available."). Revoke locks the account out indefinitely, removes its roles and permission claims, and revokes its refresh and MCP service tokens; the next request with a live access token is 401. Owners and the caller cannot be revoked. Access token is held in-memory by `AuthStore` (no localStorage); refresh token is an httpOnly cookie. `authInterceptor` attaches `Bearer` from the store and refreshes on 401. Silent refresh on app init hydrates the session from the cookie. `authGuard`/`guestGuard` protect routes. Roles and permissions: two roles, Owner and Member, each a bundle of `permission` claims (`connections.manage`, `ai.use`, `mcp.connect`, `mcp.service`, `ops.admin`, `users.manage`) in Identity's role-claim table; per-person grants are user claims. `Permissions.ByRole` is the source (Owner all, Member `connections.manage`); `RoleSeeder` converges it at startup, grants Owner to `Auth:OwnerEmail` (or the sole user) and makes every role-less account a Member, skips revoked accounts, and invites grant Member. `SmokeAccountSeeder` (startup, after the role seed) creates the post-deploy smoke's account from `Auth:SmokeAccount:{Email,Password}` as a Member marked with the `seeded-account: smoke` claim (never Owner, never an existing unmarked account, password converged each start), and `SmokeDataSeeder` gives it one fake `seeded`-provider bank account with a few transactions, which `BankAccountRepository.GetAllActiveUnscopedAsync` excludes, so no scheduler or cross-user job (snapshots, alerts, lookups) ever sees the smoke user; both unset = no seed (runbook §4). One `RequireClaim` policy per permission (`AuthPolicies`; `RequireOwner` keeps its name and maps to `ops.admin`) with a default-deny fallback. The principal is rebuilt from the account on every request, so a removed permission is 403 on the next request. Jobs acting for a user (companion wakes) check the same policies through `IUserAuthorizationChecker`. `/auth/me` (and login/refresh) return `roles` + `permissions`; the frontend's `permissionGuard` (canMatch) and shell nav/palette filtering hide what the caller lacks (UX only). The gateway sends HSTS (365 days) outside Development, and in production the session cookies are `__Host-` prefixed with a read fallback to the legacy names (`AuthCookies`).

**Broad-universe opportunity scanning (#558) — two-stage funnel, enabled in the API host.** The scan universe is no longer held-positions ∪ watchlist, and it is not the whole index either. **Stage 1 (Research, mechanical):** `ScanShortlistService` ranks the checked-in S&P 500 seed on two cheap signals — the day's percent change from the batch quote read and recent favourable street actions (upgrades, new coverage, target *raises*) over `Opportunity:ScanShortlistActionLookbackDays` — grades the top `Opportunity:ScanShortlistGradeBudget` (60) through EDGAR, and hands back the top `Opportunity:ScanShortlistSize` (40) by combined quality x surface score. No bars are read to produce it; every upstream may fail, and if they all do the shortlist is empty. **Stage 2 (Radar, expensive):** `Radar:BroadUniverseEnabled` (set `true` in `backend/src/FinanceSentry.API/appsettings.json`; override with `Radar__BroadUniverseEnabled=true`) makes `RadarUniverseService` append *that shortlist* as `UniverseKind.IndexConstituent` members — ownership kinds still win, so a shortlisted name you hold stays a `Holding`. The nightly `radar-ingestion` job fetches bars for exactly the active universe (book + lenses + shortlist, tens of tickers), `MarketStructureReader` computes structure for the same set, and `OpportunityScanJob` ranks it by quality x momentum (`Opportunity:ScanQualityWeight`). There is no ingestion budget and no rotation any more: the shortlist *is* the bound, pinned by `ShortlistScopedIngestionTests` and `ShortlistStructureCostTests`. The shortlist churns daily and dropped members are de-activated by the usual compose-and-deactivate path; constituents stay exempt from `RadarFreshnessWatchdogJob` (a name shortlisted today has no bars until the run that ingests it). **Turning it off** is the same key set to `false`: the next sync deactivates the shortlisted members, stage 1 is never asked for a shortlist, and the scanner falls back to the book. The seed list (`Modules.Research/Infrastructure/Resources/sp500-constituents.json`) is regenerated from the public constituents dataset and every symbol verified against the Yahoo chart endpoint — symbols are stored in Yahoo form (`BRK-B`, not `BRK.B`); never hand-edit it. **Alert fan-out** is gated the way Radar's structure scanner launched: `Opportunity:ScanAlertMode` ships `LogOnly` (set in `appsettings.json`; override with `Opportunity__ScanAlertMode=Alerting`), so a top-tier *Scan* nomination records its `top_tier_candidate` signal but raises no Alert — a widened scan clearing the bar on several unfamiliar names would otherwise interrupt once per name per user. User and Ledger nominations are deliberate acts and alert regardless. `Opportunity:ScanMaxNominationsPerRun` is 8 (was 5, set against the whole-index width); the top-decile cut stays 90 — the percentile is inclusive, so its absolute yield already shrinks with the universe. Still open (US6): a genuinely batched quote read for stage 1 (today it costs ~500 light per-ticker quote fetches a night), and keeping an active Scan candidate's bars fresh once its ticker drops off the shortlist. Spec: `specs/20260910-001634-broad-universe-scan/`.

**Scheduled policy review (#696) — DONE.** Daily Hangfire job `policy-review` (05:00 UTC, after the 04:00 action tickets; `PolicyReviewJob` in `FinanceSentry.Modules.Research/Infrastructure/Jobs/`) runs `RunPolicyReviewCommand` for every user with a current IPS. The cadence lives in the statement, not the cron: `PolicyReviewSchedule` reads the current version's `ReviewCadence` (`PolicyReviewCadence`: monthly / quarterly / semi-annual / annual; unrecognised → annual, flagged) and anchors on the latest `LastReviewedAt` across every version (never reviewed → the first version's `CreatedAt`), so saving a new version does not restart the clock. When due, the handler reads `GetAllocationDriftQuery` (targets and bands from the IPS only); an empty (no valued positions) or stale book defers the review — nothing is recorded, `LastReviewedAt` is not stamped, and the next daily run retries. Otherwise it builds the structured proposal with the pure `PolicyReviewProposer` (per-sleeve drift, `Trim`/`Add`/`Review` adjustments sized back to target, per-sleeve and overall rationale), and the `PolicyReview` alert is raised **before** `IPolicyReviewRepository.RecordAsync` writes the `research.policy_reviews` row (M017) and the reviewed statement's `LastReviewedAt` in one unit of work — so a failed alert leaves the review unrecorded for the next run to retry. The review id is derived deterministically from (user, statement, due date), so a retry after a failed record hits the alert's `OncePerReference` dedup instead of duplicating it. The proposal reaches the operator as that alert (Info when within bands, Warning with adjustments) → Companion (`CompanionEventKind.PolicyReview`, in the wake dispatcher's `ProposalKinds` so it asks for acknowledgement). A review still unopened more than 2 days past due is reported first as a `PolicyReviewMissed` Warning (`OncePerReference` per due date), even if the catch-up review then fails. Recommend-only: the review path has no dependency that can place, stage or route an order (a constructor-dependency test guards it). MCP read: `get_policy_review`.
